# Async AI Jobs & State Storage on Vercel — September 2026 Research Report

## 1. Job execution models on Vercel today

**Verdict:** For this app's workload (single/few Anthropic calls, 10–60s generation, streamed to the requester, cached for reuse), the simplest correct model is **(a) a plain streaming Fluid-compute function that generates on demand and persists with `waitUntil`**, with **Vercel Workflows** as the upgrade path once you add fact-checking/multi-step pipelines or need durable retries across deploys. Queues and QStash are solutions to a problem you don't yet have (fan-out/decoupling); Cron is only useful for sweeps/cache invalidation, not job execution.

- **(a) Plain streaming function + `waitUntil`:** Available on Hobby. Default max duration 300s (5 min) on Hobby as of the current docs generation (`last_updated: 2026-08-24`); Pro/Enterprise default 300s, GA max 800s, beta extended max 1800s (Node/Bun/Python only, per-function config required above 800s). `waitUntil()` (from `@vercel/functions`) extends execution to flush a write after the response starts, but the promise is bounded by the *same* max duration as the request — it does not get extra time. Works identically in `vercel dev`. [Configuring Maximum Duration](https://vercel.com/docs/functions/configuring-functions/duration) (updated 2026-08-24), [waitUntil changelog](https://vercel.com/changelog/waituntil-is-now-available-for-vercel-functions).
- **(b) Vercel Workflows (Workflow SDK, `"use workflow"`/`"use step"`):** **Public beta** (per Vercel's own changelog: "Open source Workflow Development Kit is now in public beta"). Built on Vercel Queues + "managed persistence." No max *run* duration or *sleep* duration limit; a single step's runtime is still capped by normal Function limits; a workflow *orchestration replay* is capped at 240s. Retries are automatic at step boundaries. Streaming: the SDK has first-class `streaming` primitives that persist stream chunks (10MB/chunk, 1000 chunks/sec) so a client can attach mid-run or after a redeploy. **Local dev**: zero-config "Local World" — stores state as JSON under `.workflow-data/`, runs steps synchronously in-process, no server needed for unit tests; `npx workflow web` gives a local trace UI. **Hobby**: yes — Hobby gets 50,000 Workflow Events/month and 1GB Data Written free, but **Workflow Data Retained is not available on Hobby at all** (state is only kept 1 day after run completion on Hobby vs 7 days Pro / 30 days Enterprise) — meaning stored workflow *run history* isn't a durable cache substitute on Hobby; use it for orchestration, not as your results store. [Vercel Workflows](https://vercel.com/docs/workflows) (2026-09-04), [Pricing/Limits](https://vercel.com/docs/workflows/pricing) (2026-06-16), [Local World](https://useworkflow.dev/docs/deploying/world/local-world).
- **(c) Vercel Queues:** **Public beta** since Feb 27, 2026 ([changelog](https://vercel.com/changelog/vercel-queues-now-in-public-beta)); Python SDK beta added Aug 19, 2026. At-least-once delivery, push-mode consumers are private (no public URL), visibility timeout 0–3600s (default 60s), message TTL 60s–7 days, built-in idempotency-key dedup at publish time, no native DLQ (app-level via retry callback). Works locally with `next dev`/`vercel dev` — messages go to the real hosted Queues service but callbacks invoke your handler in-process. Billed per 4KiB-chunk operation; consumer function compute billed separately. Good building block if you later want decoupled fan-out (e.g., "summarize + fact-check + reader-mode" as independent consumers), but overkill for a single request/response cache-fill. [Queues concepts](https://vercel.com/docs/queues/concepts) / [pricing](https://vercel.com/docs/queues/pricing) (both 2026-08-12).
- **(d) Upstash QStash / Upstash Workflow:** Third-party alternative available via Marketplace (`vercel.com/marketplace/upstash/upstash-qstash`). Provides `context.call`, `context.waitForEvent`, `context.notify`, automatic retries, and a `logs()` API. Functionally overlaps almost entirely with Vercel Workflows/Queues now that those are first-party — worth using only if you specifically want a workflow engine that isn't tied to Vercel (portability) or want QStash's HTTP-based scheduling from outside Vercel. Adds a second vendor/billing relationship for a solo dev with no clear win here. [Upstash Workflow overview](https://upstash.com/docs/qstash/sdks/ts/overview).
- **(e) Vercel Cron:** Available on **all plans including Hobby**, up to 100 cron jobs/project on every plan now. Triggers a GET to a Function on a schedule (UTC only, no `MON`/`JAN` aliases). Use it only for the "sweep stale cache entries" / "recompute drifted-thread summaries" maintenance job, not for driving the AI call itself — a cron-triggered function has the same duration limits as any other Function. [Cron Jobs docs](https://vercel.com/docs/cron-jobs) (2026-08-11).

## 2. Storage options for job state and stored summaries

**Verdict:** Use **Redis via Vercel Marketplace (Upstash Redis)** as the primary store for both enrichment results and job-status records — it natively supports TTL and sorted sets (for "newest summary for item X"), has sub-millisecond–low-single-digit-ms latency, and has a genuine free tier usable from Hobby. Use **Neon Postgres** only if/when you need relational querying across many items (e.g., admin dashboards, fact-check history) — it's a fine *secondary* store, not a replacement for the hot cache path. **Vercel KV is dead** — don't design around it.

- **Vercel KV:** Deprecated. New KV stores cannot be provisioned; existing ones were auto-migrated to Upstash Redis in December 2024; the `@vercel/kv` npm package hasn't shipped since Sept 2024 and is marked deprecated. [Redis on Vercel](https://vercel.com/docs/redis) (2026-01-13).
- **Upstash Redis (via Marketplace or direct):** Free tier (Sept 2026, per Upstash's own pricing/blog): 500K commands/month, 256MB data, 10GB monthly bandwidth, storage cap raised to 100GB on paid tiers. Full Redis command set (sorted sets, `EXPIRE`/TTL, `SET NX EX` locks). Latency: sub-0.5ms p50 same-region, ~1–1.5ms cross-AZ in comparative benchmarks. Query pattern "newest row for item X of kind Y": trivially a sorted set keyed by `item:{id}:{kind}` scored by `generatedAt`, or a simple string key `item:{id}:{kind}:latest` holding a pointer to the versioned hash — both are natural Redis idioms; no primary source gives an exact SLA number for cross-region Marketplace latency, flagged below. Local dev: no official in-memory/Docker emulator documented by Upstash or Vercel; the practical pattern (not vendor-documented) is to fall back to an in-process Map when `REDIS_URL`/`KV_REST_API_URL` env vars are absent. [Marketplace storage](https://vercel.com/docs/marketplace-storage) (2026-08-11), Upstash pricing/blog search results (Sept 2026, secondary sources — could not load upstash.com/docs/redis primary TTL/sorted-set page directly, flagged).
- **Vercel Blob:** Object storage (S3-backed), 11 nines durability, private/public modes, conditional writes (`ifMatch` ETag) for optimistic concurrency, `list()` with prefix (lexicographic, not time order — must encode timestamp in the key to sort by recency). CDN caches blobs up to 1 month by default; updates take **up to 60 seconds to propagate** through Vercel's cache (bypassable server-side with `useCache: false` on private reads). No TTL/auto-expiry primitive — you'd delete manually or via cron. This is a reasonable place to persist the *rendered summary text* as an artifact if you want cheap, durable storage independent of Redis eviction, but it's a poor fit as the *index* (no query-by-recency, no atomic dedup lock). [Vercel Blob](https://vercel.com/docs/vercel-blob) (2026-08-26).
- **Neon Postgres via Marketplace:** Free tier (Neon direct pricing, Oct 2025 change): 100 CU-hours/month compute (doubled from 50), 0.5GB storage per branch. Vercel's own Hobby-plan Postgres offering is Neon under the hood ("Vercel Postgres was Neon all along," retired as a distinct product Dec 2024). SQL gives you exactly the "newest row for item X of kind Y" query via `ORDER BY generated_at DESC LIMIT 1` with an index on `(item_id, kind, generated_at)` — more natural than Redis for this if you also want history/audit trail. Caveat: Neon's pooled endpoint uses PgBouncer in transaction mode, so **session-scoped Postgres advisory locks do not work over the pooled connection** — you'd need the direct (unpooled) hostname for advisory locks, which reintroduces serverless connection-exhaustion risk. Local dev/tests: Neon branching gives cheap ephemeral databases, but there's no documented zero-network in-memory fallback (unlike SQLite); tests either need a branch or a mock. [Neon transition guide](https://neon.com/docs/guides/vercel-postgres-transition-guide); [Marketplace storage](https://vercel.com/docs/marketplace-storage); PgBouncer/advisory-lock behavior via Neon FAQs (secondary, consistent across multiple Neon-authored pages, not independently verified on a single canonical doc page — flagged).
- **Global Config (formerly Edge Config):** Read-optimized (P99 <15ms, often <1ms), but **write-path is not built for frequent updates** — it's explicitly positioned for "frequently read, infrequently updated" data like flags/redirects, with writes going through the REST API and no TTL or per-item locking primitives. Wrong tool for job state or per-item summaries that update every time someone requests a fresh thread summary. [Global Config](https://vercel.com/docs/global-config) (2026-08-17, renamed from Edge Config).

**Recommendation:**
- (i) Enrichment results (`item:{id}:{kind}` → `{generatedAt, inputKey, text}`, plus a sorted set `item:{id}:{kind}:versions` scored by `generatedAt` for "newest ≤15%-drift" lookups) → **Upstash Redis**.
- (ii) Job status records (`job:{id}` → `{state, startedAt, error}`) with TTL → **same Upstash Redis instance**, using Redis native `EXPIRE`.
- **Yes, keep both in the same store.** Splitting adds an operational dependency and a consistency problem (job flips to "complete" in one store while the result write to another store hasn't landed) for no benefit at this scale; Redis's native TTL and atomic `SET NX EX` cover both use cases well.

## 3. Streaming from a Vercel function to the browser

**Verdict:** SSE via `ReadableStream` works on Fluid compute and is Vercel's documented, recommended pattern (via the AI SDK's `toTextStreamResponse`), but **you must explicitly set `Cache-Control: no-store`** — nothing does this for you by default, and CDN caching of a streamed response is not merely possible, it's the default failure mode people hit.

- Duration: bounded by the same Function `maxDuration` as any request (Hobby 300s default/max; Pro/Enterprise 800s GA, 1800s beta) — plenty for a 10–60s summary stream. [Streaming docs](https://vercel.com/docs/functions/streaming-functions) (2026-09-01).
- Idle/keepalive: for long-lived HTTP/2 connections, Vercel sends connection-level `PING` frames while idle; **HTTP/1.1 has no equivalent**, so HTTP/1.1 clients or intermediate proxies can still drop an idle connection — Vercel's own guidance is to "stream progress or heartbeat data while work is running" for exactly this reason. [Extended max duration beta note](https://vercel.com/docs/functions/configuring-functions/duration).
- CDN caching of streamed responses: Vercel's CDN cache criteria explicitly exclude responses with `private`, `no-cache`, or `no-store` in `Cache-Control` — but a response with *no* `Cache-Control` header, or one with `s-maxage`, **is cacheable**, up to 20MB for streaming functions specifically (vs 10MB non-streaming), for up to 1 year. This means an unguarded streaming endpoint can be cached and replayed to a different user — set `Cache-Control: no-store` explicitly on every streaming response. [CDN Cache docs](https://vercel.com/docs/caching/cdn-cache) (2026-08-11).
- EventSource vs `fetch` streaming: not documented by Vercel directly (secondary sources only). The commonly reported production issue is that intermediary proxies/CDNs buffer `text/event-stream` responses meant to be chunked, causing "nothing, then everything at once" — mitigated by `Cache-Control: no-store` plus (framework-dependent) avoiding any buffered-response codepath (e.g., in Next.js, don't `await` before returning the `Response`). Native `EventSource` cannot send custom headers or a POST body, so most AI-streaming implementations use `fetch` + manual `ReadableStream` reading rather than `EventSource`. **Flagged: not confirmed on a Vercel primary-source page** — this is standard web-platform behavior corroborated by multiple secondary sources, not something Vercel docs state outright.

## 4. Concurrency and dedup

**Verdict:** A **Redis `SET NX EX` lock keyed by `item:{id}:{kind}:{inputHash}`**, released by the request that wins, with all other concurrent requesters polling/subscribing for the result, is the simplest correct scheme and matches the primitives Vercel/Upstash already document.

- Redis `SET lock:<key> <token> NX EX <ttl>` is the standard atomic acquire; release should be a Lua script checking the token before `DEL` to avoid releasing a lock you don't own. Upstash ships `@upstash/lock` as a packaged implementation of this exact pattern. [Upstash Lock blog](https://upstash.com/blog/lock).
- Vercel Queues has a built-in **idempotency key** on publish (dedup window = message TTL, up to 7 days) — useful if the job is queue-driven, but doesn't help the "two simultaneous HTTP viewers" case directly since it dedups *publishes*, not concurrent *reads*.
- Postgres advisory locks are the SQL-native equivalent but require a **direct (non-pooled) Neon connection** since PgBouncer transaction-mode pooling breaks session-scoped locks — an added footgun for a serverless deployment that should generally use the pooled endpoint.
- Recommended scheme: on a summary request, first check Redis for a fresh cached result (age check per §6). On miss, attempt `SET job:{key} inflight NX EX 90`. Winner starts generating and streams directly to its own caller while writing chunks/final result to Redis as it goes; losers either (a) poll `job:{key}` every ~500ms–1s and then stream/replay the cached result once `state=complete`, or (b) if you adopt Workflows' streaming primitive, subscribe to the same run's stream so every viewer gets live tokens, not just the first requester.

## 5. Secrets

**Verdict:** Store `ANTHROPIC_API_KEY` as a **Sensitive (encrypted) environment variable**, scoped to **Production only**, and never populate it in Preview or the local `.env` — this is enforceable natively and matters more than usual given a real 2026 incident.

- Sensitive env vars are **write-only after creation** — the plaintext is never shown again in the dashboard, and build logs auto-redact values ≥32 chars as `[REDACTED]`. They can only be created for **Production and Preview** environments (not Development) — meaning if you deliberately *omit* the key from Preview, there's no accidental leak path into preview deployments. [Sensitive environment variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables) (2026-08-28).
- Context: on **April 19, 2026**, Vercel disclosed a security incident (OAuth supply-chain compromise via a third party named Context.ai) in which **non-sensitive** env vars were exposed because they're stored differently (not encrypted the same way as Sensitive-typed vars); Vercel's post-incident guidance was to rotate anything not stored as a Sensitive/Secret-typed var. This is a direct, current argument for typing the Anthropic key as Sensitive rather than a plain env var. (Secondary source reporting on the bulletin — flagged as not independently re-verified against Vercel's own incident bulletin page, which wasn't fetched directly.)
- Local/dev: Development-environment variables live in `.env.local` / are pulled via `vercel env pull` or auto-injected by `vercel dev`. Simply **don't add `ANTHROPIC_API_KEY` to the Development environment at all** — code should treat its absence as "AI disabled" (mock/stub responses in tests) rather than throwing, so CI and local runs never call the real API and never spend money. [Environment variables](https://vercel.com/docs/environment-variables) (2026-08-20).

## 6. Recommended architecture (≈20 lines)

```
Endpoints:
  POST /api/enrich/:kind          -> checks cache, starts job if needed, kicks off streaming
  GET  /api/enrich/:kind/stream   -> SSE (ReadableStream), Cache-Control: no-store, reads live tokens
  GET  /api/enrich/:kind/status   -> polling fallback (state, cached result if complete)
  GET  /api/cron/sweep            -> Vercel Cron, expires/recomputes drifted entries

Store: single Upstash Redis (Marketplace). Keys:
  result:{itemId}:{kind}          hash {generatedAt, inputHash, threadSize, text}  (no TTL; overwritten on refresh)
  job:{itemId}:{kind}             string {state, startedAt}  EX 90s (auto-clears stuck jobs)
  lock:{itemId}:{kind}            SET NX EX 90  (dedup)

Lifecycle: requested -> lock acquired -> job:state=running -> generate via Anthropic,
  streaming chunks to caller + appending to a Redis list/stream -> on success:
  result:* written, job:state=complete, lock released -> on error: job:state=error, lock released.
  Cache hit path: if result.threadSize within 15% of current thread size, serve cached
  text immediately (no lock, no call to Anthropic).

Client: opens SSE stream; if a job is already `running`, subscribe to the same stream
  (or poll /status every ~1s) instead of starting a new one — never re-trigger generation
  while lock:{key} exists.

Local/e2e: if REDIS_URL / KV_REST_API_URL is unset, use an in-process Map-based store with
  the same interface (no TTL sweep needed for short-lived test runs); ANTHROPIC_API_KEY
  absent -> return a canned/mocked stream so tests never call the real API.

Fallback if Redis is ever unavailable on Hobby (it isn't today, but as a hedge):
  Neon Postgres (Hobby-tier Marketplace) table `enrichments(item_id, kind, generated_at,
  input_key, text)` with an index on (item_id, kind, generated_at DESC) replaces the
  result store; dedup falls back to a `SELECT ... FOR UPDATE SKIP LOCKED` or a unique
  constraint + upsert race instead of Redis SET NX (avoid session advisory locks over
  the pooled connection).
```

## Recommendations
1. Ship v1 with **plain streaming Function + `waitUntil`-flushed Redis write**, skip Workflows/Queues entirely — matches the DynamoDB+Lambda+SSE mental model 1:1 with less infra.
2. Adopt **Vercel Workflows** only when fact-checking/reader-mode need multi-step retries, human-in-the-loop, or sleeps spanning minutes+ — it's public beta, not GA, and Hobby doesn't retain workflow run data long-term, so don't lean on it as your cache.
3. **Upstash Redis (Marketplace)** as the single store for both results and job state; keep Neon in your back pocket only if you later want SQL analytics over enrichment history.
4. Explicit `Cache-Control: no-store` on every streaming route — this is the single most likely production bug given Vercel's CDN caches streaming responses up to 20MB/1yr by default when headers don't forbid it.
5. Type `ANTHROPIC_API_KEY` as **Sensitive**, Production-only; leave it absent from Preview/Development so tests and preview deploys structurally cannot spend money.

## Open questions / risks
- **Not confirmed on a primary Upstash doc page**: exact TTL/sorted-set docs page (upstash.com/docs/redis) — pricing/feature claims above are cross-checked via Upstash's own blog/pricing posts (Sept 2026) but not the redis-command reference itself.
- **Not confirmed on a Vercel primary source**: the April 2026 "Context.ai" security-incident details — sourced from secondary reporting (TrendAI/Trend Micro), not Vercel's own bulletin page, which was not fetched. Worth verifying directly before citing externally.
- **EventSource vs fetch-stream buffering behavior** is standard web-platform/CDN knowledge, not stated on a Vercel doc page — verify empirically against your own CDN response headers before relying on it in the plan.
- Vercel Workflows' **240s replay-duration limit** and event-count limits (25,000 events/run, 10,000 steps/run) matter only if a workflow's *own orchestration logic* grows complex — irrelevant to a single/few-step summarization job, but worth remembering if fact-checking becomes a long fan-out pipeline.
- Marketplace Redis cross-region latency from a Vercel Function isn't published as an SLA by either party — pick the Upstash region matching your Function region and measure.
